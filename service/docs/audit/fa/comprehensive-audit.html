۲. خلاصه مدیریتی

ممیزی حاضر به‌صورت مستقل، سوروس_SERVICE را در برابر SDK مرجع صحه‌سنجی کرد. همه‌ی قابلیت‌های آفلاین‌قابل‌آزمون اجرا و با شواهد قابل‌بازتولید مستند شدند. یک نقص واقعی در لایه آداپتور (ترتیب ناپایدار state کانال‌ها در blob نشست) کشف و اصلاح شد؛ و یک نشت کلید توسعه در فایل compose حذف شد.

انطباق با SDK: تمام ۲۴ قابلیتِ به‌کاررفته‌ی SDK در سرویس، با جدول انطباق و تست‌های افتراقی (شامل round-trip بایت‌سطحِ نشست و جدول کامل مپ خطا) پشتیبانی می‌شوند. هیچ قابلیتی اختراع نشده؛ عملیات‌های پشتیبانی‌نشده صریحاً UNSUPPORTED برگردانده می‌شوند.

آنچه صحه‌سنجی نشده: رفتار در برابر سرویس واقعی Soroush Plus (احراز هویت OTP، پیام‌رسانی، رسانه، بازیابی نشست واقعی) — به‌صورت سیستماتیک BLOCKED_NO_LIVE_ACCOUNT طبقه‌بندی شده است.

نتیجه صلاحیت production: به‌صورت صادقانه، صلاحیت production کامل نشده است. سه ورودی بیرونی باقی است: (۱) اعتبارنامه واقعی Soroush Plus، (۲) تصمیم مالک روی KMS، (۳) مجوز انتشار. همه مسیرهای آفلاین سبز هستند.

۳. معماری واقعی میکروسرویس

۳.۱ مرزبندی لایه‌ها (Hexagonal)

ساختار پیاده‌شده دقیقاً مطابق طرح مصوب فاز ۲۴ است. لایه domain کاملاً خالص است و تست مرزی TestDomainDependencyBoundary (از طریق go list -deps) وارد شدن SDK/protobuf/gRPC را در سطح CI مسدود می‌کند.

cmd/service → app (state machine) → resources:
  storage (PostgreSQL + migrations)
  crypto (KEK provider)
  gateway (upstream.Factory)
  runtime (Manager + use cases + gRPC server)

internal/domain        ← هیچ import از SDK/grpc/proto (تست مرزی)
internal/ports         ← interface ها (فقط domain)
internal/application   ← Runner/Manager/hub/use cases
internal/infrastructure↔ upstream (SDK) · persistence (pgx) · cryptography
internal/grpcapi       ← server + interceptors + handlers + errors

۳.۲ نقاط قوت

  • تک‌درِ SDK: فقط internal/infrastructure/upstream ماژول SDK را import می‌کند (تست‌شده).
  • مالکیت صریح منابع: هر goroutine صاحب مشخص دارد؛ Stop همیشه با cleanup معکوس همراه است.
  • صف‌های bounded با سیاست سرریز صریح در همه‌جا.
  • سیاست ابهام mutation (عدم retry خودکار) در یک نقطه متمرکز (Runner) اعمال می‌شود.

۳.۳ نقاط ضعف شناسایی‌شده

  • StreamAccountEvents در v1 با polling (۲ ثانیه) پیاده شده است، نه push ترنزیشنی — محدودیت مستند شده و در S5 جایگزین خواهد شد.
  • ListDialogs توکن ادامه‌ی خود را روی top_message میسازد (مستند)؛ صفحه‌بندی عمیق‌تر نیازمند offset-peer است.
  • single-replica: مالکیت توزیع‌شده (lease + fencing) طراحی شده ولی پیاده نشده (ADR-0002/0007).

۴.۱ یافته‌ی مهم: نقص ترتیب state کانال‌ها (اصلاح‌شده)

۴.۲ انطباق نشست (Session)

فرمت blob سرویس (JSON v1: کلید/DC/پرچم احراز/update-frontier/کانال‌ها) با یک نشست واقعی SDK (ساخته‌شده با sdksession.NewWithKey + SetDC + SetAuthorized + SetUpdateState + دو کانال) round-trip شد: کلید (KeyID + بایت‌ها)، DC، پرچم، frontier و کانال‌ها همه حفظ شدند. رفتار پس از SetUnauthorized (لغو احراز) نیز صحه‌سنجی شد: کلید می‌ماند، پرچم authorized پاک می‌شود — دقیقاً مطابق معناشناسی SDK. ورودی‌های خراب (۵ حالت) همگی با ErrCrypto fail-closed می‌شوند.

محدودیت: «بازیابی واقعی نشست در برابر سرور» به حساب واقعی نیاز دارد و BLOCKED_NO_LIVE_ACCOUNT است.

۵. تحلیل Protocol Buffers و gRPC

  • لینت: buf lint پاک (STANDARD منهای دو قاعده‌ی نام‌گذاری streaming — موندокумент در buf.yaml).
  • drift: buf generate + مقایسه با gen/ — پاک (تکرارشونده).
  • ids: message_id به‌صورت رشته‌ی اعشاری (مصون از JS unsafe integer)؛ تست TestFormatID_DecimalStrings عدد ۲⁵³+۱ را pin می‌کند.
  • ErrorInfo: ۱۷ reason پایدار؛ جدول کامل در error-mapping-matrix.csv.
  • health بدون احراز هویت (فقط SERVING) — تست شده؛ reflection پیش‌فرض خاموش.
  • deadline: تعلق و پیش‌нять caller deadline تست شده (TestDeadline_CallerDeadlineWins).

۶. تحلیل AccountRunner و Concurrency

  • mutation queue با عمق پیکربندی‌پذیر (پیش‌فرض ۶۴) و reject صریح (ErrTooManyRequests) — تست اشباع: ۱۰/۱۰ submit در حالت اشباع رد شد.
  • pump تک‌نخی: تست ۲۰۰ mutation — بیشینه‌ی هم‌زمانی = ۱ (سریال‌سازی صحه‌سنجی شد) و ترتیب حفظ شد.
  • reads هم‌زمان با semaphore — تست: بیشینه‌ی هم‌زمانی ≥ ۲.
  • hub: publish بدون allocation، دنباله‌ی per-stream یکنوا، subscriber کند drop می‌شود (تست‌شده)، ۵ مشترک هم‌زمان همه‌ی event ها را گرفتند.
  • goroutine leak: بعد از churn (۸×۲۵ subscribe/unsubscribe) شمارش به baseline برگشت.
  • race detector: -race روی همه‌ی پکیج‌های سرویس سبز.

۷. تحلیل Authentication و Multi-Tenancy

  • کلید API به‌صورت SHA-256 hash + prefix ذخیره می‌شود؛ مقایسه‌ی candidates با زمان ثابت.
  • AuthN/AuthZ interceptor ها: تست‌شده (missing key، bad key، missing permission → PermissionDenied؛ health معاف).
  • Tenant scoping دو لایه‌ای: interceptor + باز-بررسی مالکیت در use case (تست TestManager_TenantScopedGet و تست DB).
  • تلفن فقط به‌صورت HMAC-hash + mask ذخیره می‌شود؛ فراخوانی‌های auth باید phone را دوباره بفرستند و با hash مقایسه می‌شود (تست‌شده).

۸. تحلیل Session Security و Cryptography

فرمت: SMB1 ‖ kek_ver ‖ wrapped_dek ‖ nonce ‖ ciphertext — AES-256-GCM، DEK ۳۲بایتی per-session، KEK از provider. تست‌ها: round-trip بدون plaintext-leak، دودست‌گیری در ۳ موقعیت تامپر، کلید اشتباه، rotation (ReWrap)، provider errors، KMS fail-closed. شredding با حذف ردیف (wrapped DEK همراه ردیف حذف می‌شود).

تفکیک مهم: کنترل‌های پیاده‌شده (GCM auth، version binding، rotation) با مفروضات تأییدنشده (امن‌بودن فایل KEK در دیسک، مقاومت KMS واقعی) تفکیک شده‌اند. KMS با تصمیم مالک باقی است و fail-closed می‌شود.

۹. تحلیل PostgreSQL و Data Integrity

  • Migration 0001: tenants/credentials/accounts/sessions/operations/audit + FK/CHECK/unique (شامل unique سراسری روی phone_hash — یک حساب فقط یک tenant).
  • Migrations در schema_migrations ثبت و idempotent اند.
  • کوئری‌ها همگی tenant-scoped؛ اسکن تست‌های intégration (۶ تست) در CI با postgres service container اجرا می‌شود؛ در این محیط با پیام صریح BLOCKED_ENVIRONMENT شدند.
  • هیچ transaction ای هنگام فراخوانی upstream باز نمی‌ماند (Claim/Finish دو فراخوانی جدا هستند).

۱۰. تحلیل Messaging، Media و Updates

  • Messaging: idempotency از طریق operations + fingerprint (تعارض کلید/فینگرپرینت تست‌شده در سطح DB)؛ ابهام mutation با OPERATION_AMBIGUOUS صادقانه گزارش می‌شود.
  • Media: client-streaming با قرارداد metadata-first، enforce سایز (۰، سقف ۲GiB)، chunk ≤ ۲۵۶KiB، discard partial؛ server-streaming download با clamp سایز chunk. تست‌ها همگی از طریق سرور واقعی in-process اجرا شدند.
  • Updates: at-most-once per stream (مستند)، دنباله‌ی یکنوا تست‌شده، slow-consumer drop تست‌شده، لغو تمیز تست‌شده. دنباله‌ی حساب از طریق state پایدار SDK حفظ می‌شود.

۱۱. تحلیل Error Handling و Idempotency

جدول کامل مپ (۲۲ ردیف) در error-mapping-matrix.csv. تست جدولی TestTranslate_ErrorMappingTable تمام نگاشت‌ها را با خطاهای واقعی SDK (ساخته‌شده به‌صورت typed) صحه‌سنجی می‌کند؛ شامل حفظ تعداد ثانیه‌های FLOOD_WAIT. قاعده‌ی طلایی حفظ شده: connection loss در mutation = OPERATION_AMBIGUOUS و هرگز retry خودکار.

۱۸. محدودیت‌ها و ریسک‌های باقی‌مانده

  • Live validation: همه‌ی جریان‌های احراز/پیام/رسانه در برابر سرویس واقعی صحه‌سنجی نشده‌اند.
  • KMS: پیاده‌سازی نیازمند تصمیم مالک؛ فعلاً fail-closed.
  • Single-replica: بدون lease/fencing، مقیاس افقی امن نیست (مستند).
  • ImportSession: مسیر string-session در آداپتور باقی است.
  • OTLP export: wiring عملیاتی باقی است (logger/metrics داخلی فعال‌اند).

۱۹. برنامه پیشنهادی Production Qualification

  1. تصمیم KMS + پیاده‌سازی KeyProvider تولیدی (S4-باقی).
  2. اجرای runbook live با حساب آزمایشی (اتصال → auth → نشست → پیام → رسانه → streaming).
  3. اجرای integration suite با postgres واقعی در CI (آماده).
  4. حذف replace و انتشار ماژول SDK (release policy فعال).
  5. OTLP wiring + runbook عملیاتی (S8).
  6. باز-اجرای کامل دروازه‌های release (مستند در release-process.md).
