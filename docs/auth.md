# Authentication & Authorization (Phase 9)

The auth subsystem implements Soroush Plus account login over the
Phase 1–8 foundations (transport, crypto, RPC engine, session). Its
behavior is traced line-by-line to the Python reference
(`reference/SPlusthon`, read-only); nothing is modeled from generic
MTProto documentation where the reference is precise.

**Real Soroush Plus server validation: NOT PERFORMED.** Reason: no real
account / authentication credentials are available (phone verification,
codes, potential 2FA). All evidence comes from the in-process fake
transport exercising the real protocol stack, plus golden vectors
*generated by executing the Python reference itself*. The architecture
adds real-server validation later as **tests/configuration only** — no
production change.

## Two independent axes

```
Transport lifecycle (Phase 6)          Authorization (Phase 9)
New → Disconnected → Connecting →      Unauthorized → CodePending →
Connected → Ready → Closing → Closed   PasswordRequired → Authorized →
                                       AuthorizationRevoked
```

Connected ≠ logged in. The lifecycle answers "does the MTProto session
work"; authorization answers "which account — if any — does it belong
to". They are separate state machines with separate sources of truth:

| State | Owner | Persisted |
|---|---|---|
| `AuthCodePending` / `AuthPasswordRequired` | client (`authFlow`, `authHashes`) | **no** — the reference keeps `_phone_code_hash` in memory only (auth.py:279) |
| `AuthAuthorized` | session (`session.StateAuthorized`) | **yes** — enables restart reuse |
| `AuthAuthorizationRevoked` | client (`authRevoked`, permanent-401 events) | no — re-derived from server behavior |

`AuthState()` priority: Revoked → PasswordRequired → Authorized
(session) → CodePending → Unauthorized. An authorized session stays
Authorized even if a re-login SendCode is issued.

## API

```go
type AuthState int32
const ( AuthUnauthorized AuthState = iota; AuthCodePending
        AuthPasswordRequired; AuthAuthorized; AuthAuthorizationRevoked )

func (c *Client) AuthState() AuthState
func ParsePhone(phone string) (string, error)          // utils.py:916-923
func (c *Client) SendCode(ctx, phone) (*CodeSent, error)
func (c *Client) SignIn(ctx, phone, code) (*Authorization, error)
func (c *Client) SignInWithHash(ctx, phone, code, hash) (*Authorization, error)
func (c *Client) CheckPassword(ctx, password) (*Authorization, error)
func (c *Client) LogOut(ctx) error
```

`CodeSent{PhoneCodeHash, Type, NextType, TimeoutSecs}` mirrors
`auth.SentCode`; `Authorization{User}` mirrors `auth.Authorization` (the
user comes from the server's response — never fabricated).

## State machine

```
Unauthorized ──SendCode──► CodePending ──SignIn ok──► Authorized
     ▲                        │    │
     │        PHONE_CODE_     │    └─SESSION_PASSWORD_NEEDED─► PasswordRequired
     │        EXPIRED         │                                       │
     └────────────────────────┘                              CheckPassword ok
     ▲                                                       │
     │                        (PHONE_CODE_INVALID /                       │
     │                         PASSWORD_HASH_INVALID: stay, retry)        │
     │                                                                    ▼
     └──LogOut────────────────────────────────────────────────────── Authorized

any state ──401 SESSION_REVOKED / USER_DEACTIVATED / AUTH_KEY_DUPLICATED──► Revoked
any state ──401 AUTH_KEY_UNREGISTERED / AUTH_KEY_INVALID──► Unauthorized (recoverable)
```

Failed sign-ins never mutate state (retryable); expiry drops the stored
hash (auth.py:390-392); `LogOut` RPC errors leave state untouched
(auth.py:610-612).

Documented deviations (each deliberate):

1. **Restart reuse** — the reference re-derives authorization per process
   by probing `updates.getState` (users.py:226-236); SuroMesh persists the
   authorized flag in the session (Phase 5 architecture), so a restart
   reuses authorization without any auth RPC (spec §12 requirement).
2. **Logout lifecycle** — the reference disconnects and *deletes* the
   session (auth.py:617-619, client unusable); the Go client tears the
   transport/engine down (Disconnected, keyless session persisted) and
   stays a usable object: a fresh `Connect` re-exchanges the key, then
   `SendCode`/`SignIn` work again. No authorization state survives
   (`AuthState() != Authorized` guaranteed; entities cleared — a superset
   of the reference's self-user clear, safe because the key is gone).
3. **Update bootstrap** — `_on_login` additionally loads update state
   (auth.py:457-468); in SuroMesh that is the Phase 6 update manager's
   responsibility, not the auth flow's.
4. **PHONE_NUMBER_INVALID WebSocket-close compensation** — the reference
   reconnects and re-checks authorization after this error because the
   Soroush server closes the WebSocket mid-auth (auth.py:393-426);
   SuroMesh's engine-level reconnect (Phase 3/4) handles transport
   recovery generically, so the auth flow treats the error as
   deterministic.
5. **`start()` convenience loop** — UI glue (callbacks, console prints);
   not part of the Go API. Callers compose SendCode/SignIn/CheckPassword.
6. **Unicode digits** — Python `str.isdigit` accepts non-ASCII digit
   forms; Go accepts ASCII digits only (irrelevant for E.164 phones).

## sendCode flow

```
ParsePhone → stored hash? ──no──► auth.sendCode(phone, api_id, api_hash, CodeSettings{})
                   │                    │ AUTH_RESTART → retry (≤3 total)
                   │                    │ sentCodeSuccess → ErrSendCodeSuccess
                   │                    ▼ store non-empty hash (auth.py:524-526)
                   └──yes──► auth.resendCode(phone, hash)
                                 │ PHONE_CODE_EXPIRED → drop hash, fresh send
                                 ▼ store new hash → CodeSent{...}
```

`phone_code_hash` is sensitive authentication state: held in
`c.authHashes` (in-memory), returned by the API (the reference exposes it
too), and never logged, never in errors, never in metrics.

## signIn flow

```
ParsePhone → hash (explicit ? : stored, else ErrPhoneCodeHashMissing)
→ auth.signIn(phone, hash, code)
    ├─ PHONE_CODE_INVALID            → ErrCodeInvalid      (state unchanged)
    ├─ PHONE_CODE_EXPIRED            → drop hash, ErrCodeExpired (→ Unauthorized)
    ├─ SESSION_PASSWORD_NEEDED       → ErrPasswordRequired (→ PasswordRequired)
    ├─ AuthorizationSignUpRequired   → ErrPhoneUnoccupied  (state unchanged)
    ├─ 401-class                     → handleAuthReject (session unauth / revoked)
    └─ auth.Authorization            → _on_login: seed self user,
                                       session.SetAuthorized, persist,
                                       clear flow → AuthAuthorized
```

## 2FA / SRP flow

`CheckPassword` = reference sign_in(password=…):

```
account.getPassword → validate (p, g, salts, srp_B) — BEFORE password work
  → x = SHA256(salt2 ‖ PBKDF2-HMAC-SHA512(SHA256(salt2‖SHA256(salt1‖pw‖salt1)‖salt2), salt1, 100000) ‖ salt2)
  → k = SHA256(pad256(p) ‖ pad256(g));  g_x = g^x mod p
  → a = 256 random bytes (A = g^a mod p must pass is_good_mod_exp_first, u > 0)
  → u = SHA256(pad256(A) ‖ pad256(B));  S = (B − k·g_x)^(a+u·x) mod p
  → M1 = SHA256(xor(H(pad p),H(pad g)), H(salt1), H(salt2), pad A, pad B, H(pad S))
auth.checkPassword{srp_id, A, M1}
    ├─ PASSWORD_HASH_INVALID → ErrPasswordInvalid (retryable)
    └─ auth.Authorization → _on_login
```

Every constant and step matches `password.py` (see the header comment in
`client/srp.go`). Primality uses Miller-Rabin where the reference uses
trial factorization — the same predicate (prime vs. composite).

## Session interaction

```
Start → Connect → load session ─┬─ no key → key exchange → Unauthorized
                                └─ key + authorized → reuse (no auth RPC)
Authorized → Close → restart → load session → reuse authorization
LogOut → auth.logOut → entities cleared, flow reset, key cleared,
         emptied file persisted, transport torn down (Disconnected)
```

Verification codes are never stored in the session (they live only in the
process-local `authHashes`, and even there only the *hash* — the code
itself is supplied by the caller per call).

## Cancellation & concurrency

- Every auth operation splices the caller's context with the client
  lifecycle context (`mergeContext`): caller cancellation AND `Close`
  interrupt SendCode/SignIn/CheckPassword mid-RPC and win over any retry
  sleep. Verified by `TestAuthCancellation`,
  `TestAuthStress32Cancellation`, `TestAuthStress32CloseDuringAuth`.
- Transient flow mutations are atomic; the hash map is mutex-guarded.
  Concurrent SignIns serialize at state-commit granularity: the successful
  authorization wins and failures cannot downgrade it
  (`TestAuthStress32ConcurrentSignIn`).
- After `LogOut` the transport is down; auth operations fail with
  `ErrNotReady` until `Connect` — fail loudly, never silently ride an
  unbound key.

## Retry semantics

Auth requests reuse the Phase 6/7 engine retries (`invokeAuth` wraps
`eng.Invoke`); no separate retry implementation exists. FLOOD_WAIT follows
the client-wide threshold policy (sleep-and-retry below threshold;
`AsFloodWait` above). Reference-specific behaviors: AUTH_RESTART retry
(≤3 attempts, auth.py:510-514), resend-on-expired (auth.py:536-544);
both are flow-level retries, not hidden request replays. RPC-level
rejections (PHONE_CODE_INVALID etc.) are deterministic — never retried.

## Security model

- **No logging** of phone numbers, codes, hashes, passwords, keys, or
  SRP material anywhere in the auth path (static scan: zero
  fmt.Print/log/slog in `client/auth.go`, `client/srp.go`).
- **Error surface** renders sentinel text only
  (`authRPCError.Error() → sentinel.Error()`); raw RPC details remain
  reachable via `errors.As(err, **rpc.RPCError)`.
- **Hooks/metrics** are aggregates (method names, states, counters) — no
  high-cardinality labels, no identifiers; proven by
  `TestAuthHooksCarryNoSecrets` / `TestAuthMetricsStayAggregate`.
- **SRP**: parameters validated before password processing
  (`ErrSRPParams`); server-side verifier compares M1 with
  `subtle.ConstantTimeCompare` (fake) — the client never compares
  secrets locally. The password exists only inside `computeCheck`'s
  frame; Go cannot guarantee memory erasure (documented limitation,
  docs/security.md).
- **Behavioral leak tests**: `TestAuthErrorStringsCarryNoSecrets`,
  hook/metric tests above; repository scan in the Phase 9 report.
